# GameX《打工人桌面模拟器：2026》Codex 开发提示词 V1.2

> 本文件是可直接交给 Codex 的完整开发要求。本版明确游戏定位为「高拟真桌面 + 自动职场模拟 + 低频策略决策」，并统一原方案的轮次、播放时长、加班与技术栈设定。

## 一、项目定位与不可改变的原则

开发 GameX 旗下的单机网页游戏《打工人桌面模拟器：2026》。玩家选择职业和操作系统，为一名虚拟打工人配置工作策略，随后观看其电脑像真的有人上班一样自动运行。玩家可以长时间不操作，闲暇时回来查看状态、做一次加班抉择或调整下一局策略。

**这不是手动办公游戏，也不是让玩家持续盯屏的经营游戏。** 体验目标按优先级排列：

1. **桌面拟真**：macOS / Windows 桌面、窗口、工作软件、微信和鼠标/键盘行为可信，有「一个人正在上班」的感觉。
2. **行为连贯**：微信消息、工作任务、软件操作、错误及返工必须互相影响，不能是互不关联的假动画。
3. **低频干预**：玩家在配置阶段制定策略；局内全自动执行，只有第 10 轮结束后的加班抉择影响工作结果。
4. **可复盘策略**：结算能解释哪些配置通过什么事件和状态变化影响绩效，支持历史比较与重新挑战。

不调用真实大模型、不内置推理模型、不需要玩家提供 API Key。虚拟员工使用确定性规则、事件驱动、有限状态机和种子化随机数模拟行为。

## 二、平台与技术栈

- **首发纯 Web 单页应用**，HTML / CSS / JavaScript（ES Modules），可选轻量构建工具；不引入重型游戏引擎、后端或云服务。
- 使用 DOM + CSS 绘制桌面、任务栏/Dock、菜单、软件子窗口、编辑器、表格、聊天、工作画布。
- 窗口支持拖动、缩放、最大化、最小化、层叠与任务栏恢复。窗口视觉交互只改变观看方式，不能直接修改游戏工作状态。
- Fullscreen API 在**用户明确点击进入全屏**后调用；浏览器权限或限制应优雅降级。不能声称网页可以直接控制真实操作系统或强制隐藏所有浏览器 UI。
- 两套系统外观应分别模拟桌面布局、窗口装饰、任务栏/Dock、顶部栏、通知与常见操作习惯；**不是只换配色**。游戏开始选择 Windows 或 macOS，游戏中可切换，切换只影响表现，不影响同局模拟结果。
- 使用 CSS 变量管理主题；localStorage 保存设置、策略预设、历史记录，数据量大时可迁移 IndexedDB。
- 模拟引擎与 UI、动画和持久化隔离，保留未来使用 Tauri / Electron 封装的可能性；**本版不创建 Electron 工程**。

## 三、核心游戏循环

```text
选择职业和操作系统
  → 查看任务背景 / 工作环境
  → 选择策略预设或调整四组参数
  → 选择模拟播放节奏并开始
  → 第 1～10 轮全自动运行
  → 暂停等待玩家决定是否加班
  → 第 11～12 轮全自动运行
  → 绩效结算、短板原因、关键事件与历史对比
  → 调整参数重新开始
```

- **逻辑总轮数固定 12 轮，不随播放节奏变化**；前 10 轮是常规轮，11～12 轮取决于是否加班。
- 第 10 轮结束时只询问一次「加班 / 不加班」，展示预计收益与风险，但不剧透确定性结果。玩家不在时**静静停在待决策状态**，不得倒计时自动选择或惩罚。
- 加班使后两轮可用工作产能增加，同时提高体力消耗与过劳风险，并通过状态量影响质量和人际评价；不加班则保持正常节奏。抉择**不得直接给绩效加减固定分**。
- 模拟播放可提供「快速 / 标准 / 沉浸」预设，例如约 1～2 / 10～15 / 30～60 分钟（可在实现时调整）。这些仅是**动画与事件回放时长**，不是游戏内的生产资源，不改变事件、状态和评分；不建立虚拟工时与现实时间的换算公式。至少先实现标准播放和加速/跳转。
- 支持暂停观看、加速、跳过普通演出至下一关键节点。这些操作不影响模拟结果；不得在局内编辑策略、手动处理消息、修代码或操作表格改变结果。
- 浏览器标签页后台降频、休眠或重新进入时，应基于已记录的逻辑事件与播放游标安全恢复，避免计时漂移或重复执行。先保证可暂停恢复，不要求真实后台持续渲染动画。

## 四、职业及独立工作机制

四个职业共享策略框架，但必须有不同的任务状态机与风险传导链。不能仅是同一进度条换软件皮肤。

| 职业 | 主软件 | 通讯 | 工作循环 | 专属连锁风险 |
| --- | --- | --- | --- | --- |
| 程序员 | VSCode 风格编辑器 | 微信 | 编码→调试→测试→提交 | 技术债增加后续故障和返工成本 |
| 财务 | Excel 风格表格 | 微信 | 录入→核对→公式计算→报表/审批 | 错误沿关联表格传播，合规风险放大 |
| 产品经理 | Word 风格文档 | 微信 | 收集需求→编写→评审→确认→变更 | 需求蔓延、意见冲突、反复返工 |
| 设计师 | Photoshop 风格界面 | 微信 | 理解意图→设计→提案→改稿→交付 | 审美偏好不确定、创意疲劳、反复修改 |

每局至少有一份**具体任务书**，包含任务标题、2～5 个工作子任务、难度与依赖关系、重要风险点，而不是只有一个抽象进度条。例如程序员开发订单模块、财务核对季度报表、产品经理撰写新功能 PRD、设计师制作活动主视觉。

工作环境可由种子产生少量可解释的特征（如老板管理风格、客户变更频率、任务紧急程度）；配置阶段公开足够信息供玩家判断，不要仅用无法预测的随机数决定成败。环境是本局显式输入或从种子可重复生成的结果。

## 五、四组策略参数

所有参数在开局配置阶段设置；运行时参数锁定。每项有提示，明确「好处/代价」，允许保存配置、恢复默认和选用可修改的预设（效率狂魔、质量卫士、职场达人、佛系打工等）。预设**只是填入参数，不提供隐藏属性加成**。

### A. 工作强度

| 参数 | 范围 | 主要权衡 |
| --- | --- | --- |
| 常规工作强度 | 0～100% | 越高产能越强，但体力、错误率与崩溃风险可能恶化；**不代表第 11 轮加班选择** |
| 专注模式 | 深度工作 / 多线并行 | 抗打断和单任务效率 vs 响应速度与切换成本 |
| 任务并行度 | 1～3 | 吞吐量 vs 单任务质量、任务切换损耗 |

### B. 时间分配与沟通

| 参数 | 范围 | 主要权衡 |
| --- | --- | --- |
| 主任务投入占比 | 30～90% | 主任务进度 vs 微信及杂务处理积压 |
| 微信响应方式 | 秒回 / 延迟 / 批量处理 | 人际及时性 vs 专注与中断成本 |
| 事件优先级 | 最多选装 4 条，可拖动排序 | 高优先级规则先匹配，低优先级可能被覆盖 |

优先级候选：老板消息优先、客户消息优先、主任务剩余进度低于 20% 时忽略非紧急消息、未读超过 5 条时批量处理、同事求助一律响应、同事求助一律推迟。互斥规则不可同时装入，规则冲突要有可解释的执行顺序。

### C. 质量与风险

| 参数 | 选项或范围 | 主要权衡 |
| --- | --- | --- |
| 需求变更接受度 | 0～100% | 满意度与合作机会 vs 返工、范围失控 |
| 质量偏好 | 快速交付 / 平衡 / 精雕细琢 | 速度 vs 错误率与耗时 |
| 自测/复核频率 | 从不 / 关键节点 / 每步 | 早发现问题 vs 工作时间占用 |
| 合规/红线容忍度 | 零容忍 / 灵活 / 铤而走险 | 交付灵活性 vs 风险事件和严重后果 |

### D. 职业专属

- 程序员：技术债容忍度、需求变更时是否重构、Code Review 严格度。
- 财务：公式核查频率、异常数据上报意愿、是否绕过审批链。
- 产品经理：需求文档详细度、干系人优先级、会议参与度。
- 设计师：改稿轮次上限、多方案对冲开关、客户意图猜测策略。

设计为具有非线性和条件联动的系统，避免「把所有值拉满」获得稳定最好成绩；也不要机械地保证任何配置永远无法成为某个具体环境中的最优解。

## 六、高拟真桌面与自动操作表现（重点）

### 桌面外壳

- Windows/macOS 风格的桌面、壁纸、桌面图标、系统栏/任务栏、时钟、通知、软件窗口装饰、窗口切换及层叠；系统外观切换不重置模拟。
- 首局能够看到多个已打开窗口，工作软件为主，微信持续出现有上下文的消息；模拟鼠标指针移动、点击、选区、光标闪烁、打字、撤销、切换应用。
- **避免无意义的随机乱点或无休止重复输入**。每次可见操作对应引擎生成的工作动作，例如修改公式、写入函数、调整图层、回微信。
- 若玩家正在拖动窗口或查看日志，自动演出的模拟光标和系统窗口应采取不抢夺真实指针控制权的方式（独立视觉光标、动画层等）；绝不实际移动用户操作系统鼠标。

### 软件拟真要求

- **VSCode**：文件树、代码选项卡、语法高亮、编辑光标、终端、测试与错误提示、模拟提交；开发/调试/修 Bug 应改变对应文件片段和任务状态。
- **Excel**：行列网格、单元格选择、公式栏、多个关联工作表、模拟核查及错误传播；工作状态与单元格表现对应。
- **Word**：文档正文、标题段落、修订、批注、需求列表；需求变更应在文档内留下痕迹。
- **Photoshop**：画布、图层、属性面板、工具栏、可理解的设计变化和改稿版本；允许使用预制原创素材组合与参数化表现，不要求复刻完整图像编辑器。
- **微信**：对话列表、联系人、未读角标、通知、群聊及一对一消息、自动回复/延期/批处理；内容需引用当前任务与事件，回复符合玩家配置。

所有窗口的内容均为**游戏内仿真界面**，不是实际启动官方软件。可参考布局和操作习惯，但避免直接使用受限制的软件素材；必要时用自制图标、原创界面元素。

### 「事件→行动→画面」必须闭环

例如：产品需求变更消息到达 → 优先级规则决定是否立即回复 → 工作动作队列切换到微信 → 自动生成对应回复或保留未读 → 若接受变更，编辑器或文档实际显示后续修改 → 进度、返工、满意度变化 → 日志记录完整因果链。

这套机制应由统一的模拟事件流驱动。**不能**让 DOM 自己随机播放看起来像工作但与引擎结果无关的动画。

## 七、12 轮模拟引擎

- 输入：职业、任务书/环境、全部参数、随机种子、第 10 轮加班选择。
- 输出：12 轮状态快照、按顺序的语义动作队列、带因果信息的事件日志、最终绩效明细。
- 使用 mulberry32 或同类确定性 PRNG；**同种子 + 同职业任务环境 + 同配置 + 同加班选择必须生成完全相同的逻辑输出**。操作系统、动画播放速度、窗口位置不能影响结果。
- 每轮推进任务进度、体力、错误率、返工、未读压力、打断成本、老板/客户/同事关系与职业专属状态。
- 消息和任务事件具有来源、紧急度、截止条件、工作关联项；优先级规则决定响应顺序，质量/风险参数决定动作策略。
- 使用有限状态机组织工作步骤；计算可先完成，再以语义动作事件驱动动画回放。
- 第 10 轮后引擎进入 `awaiting_overtime_choice`；收到选择才计算或确认余下两轮，不得在等待期间丢失状态。
- 引擎纯函数，不访问 DOM、不依赖真实墙上时间、不调用网络；UI 用独立控制器播放状态和动作。
- 单局内允许老板因反复秒回而提高响应期待、同事因本局互动改变行为；**本版 NPC 不记住上一局**，跨局仅保留历史记录。

每条日志至少包含：`round`、`eventId`、`source`、`action`、`triggeredRule`、`stateDelta`、`consequence`、`relatedTaskId`；支持追溯为什么本次行动发生。

## 八、终局结算与历史

完成第 12 轮后结算绩效总评 `0～100`，映射 `S/A/B/C/D`。由以下维度加权：

1. 任务交付（完成度、关键任务、错误和返工）
2. 老板满意度
3. 客户满意度
4. 同事好感
5. 体力和过劳状态
6. 职业专属代价（技术债、合规风险、需求失控或创意疲劳）

各权重和转换公式在代码中清晰注释，可依职业微调，但不允许单项决定全局评级。显示分项成绩、拖后腿的维度、影响较大的 5～8 条事件及其因果链。额外展示工作强度/体力成本和绩效效率，作为辅助指标，**不替代综合绩效主评分**。

历史保存职业、种子、环境、配置、加班选择、得分、分项与关键事件；支持比较相同种子不同配置以及同配置不同种子的结果。基础版本不做晋升、养成、剧情分支、隐藏结局或跨局 NPC 记忆；批量模拟属于后续增强，不妨碍架构预留。

## 九、界面及交互结构

1. **职业与系统选择**：四职业卡片、特点、对应软件；选择 macOS / Windows。
2. **策略配置**：四组参数、可拖拽优先级、可修改预设、可理解的 trade-off 提示；展示当局任务与已知环境。
3. **拟真桌面运行**：多窗口、自动光标和语义动作、微信通知、轮次及轻量状态组件；可自由查看/整理窗口、控制观看节奏，但不能干预工作结果。
4. **加班决定**：第 10 轮后唯一改变局内决策的弹窗；无时间限制，支持等待后继续。
5. **绩效报告**：总评分、等级、各项指标、短板原因、关键事件与重新配置。
6. **历史对比**：历史列表、筛选、两局及以上的关键指标对照。

默认让桌面成为主视觉；不要将大量仪表盘覆盖在软件上。状态和日志可以从任务栏小组件或可收起侧栏查看。演示与运行阶段都要保证即使玩家不操作，窗口仍有自然、连贯的工作行为。

## 十、防收敛与策略真实性

1. 加班收益与代价受职业、任务剩余量、体力和环境影响。
2. 频繁秒回可能提高老板期待，但也引入更严重的打断成本。
3. 配置组合存在阈值或非线性效果，例如高强度 + 多线并行 + 秒回可能引发效率崩塌。
4. 不同种子/环境带来事件差异；高风险策略不仅影响平均成绩，也应增加波动。
5. 任务与环境显式参与决策，让局内变化可解释，而不是用纯随机噪声破坏策略。
6. 对比至少 3 组代表性配置、多个种子和环境，检查策略表现差异。不得以硬编码惩罚第一名的方式强制平衡。

### 未来目标与示例

玩家仍主要配置并观察一名选定职业的打工人，但其余三个职业成为拥有独立任务、工作进度、软件操作和行为策略的 NPC，共同推进一份共享项目。

示例事件链：产品经理在 Word 中编写需求并发微信给程序员 → 程序员在 VSCode 中开发，遇到界面问题向设计师询问 → 设计师在 PS 中设计和改稿 → 财务在 Excel 中审核预算、指出超支 → 产品经理调整需求 → 程序员根据自身策略接受变更、返工或提出异议。**各职业的可见操作、消息与项目状态必须一致**，不能独立随机播放。

### 未来技术方案

1. **共享项目与交付物模型**：需求、设计稿、代码、预算、截止条件拥有统一 ID、状态和任务依赖关系。
2. **独立职业 NPC 状态机**：每个角色拥有工作队列、策略、当前动作、疲劳与职业特性，尽量复用已经完成的单职业引擎。
3. **消息/交付协议**：通过 `sender`、`recipient`、`taskId`、`artifactId`、`intent` 等语义事件协调，不直接任意修改其他角色状态。
4. **冲突与循环保护**：支持沟通延迟、资源冲突、需求变更与返工，同时防止消息风暴、无限往返和任务死锁。
5. **观赏与确定性**：主角桌面优先承载协作可视化；同种子、环境、全部角色配置应有可复现的逻辑结果，动画播放不影响计算。
6. **技术边界**：事件队列 + 规则模板 + 有限状态机 + 种子化随机数；不依赖真实大模型或后端。
