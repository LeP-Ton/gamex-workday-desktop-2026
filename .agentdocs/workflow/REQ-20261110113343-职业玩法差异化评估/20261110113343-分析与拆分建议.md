这些是已实现的不同模型，不能把现状概括为只有四套软件外观。

### 仍然高度共用的部分

1. [开局策略](../../../data/parameters.js)主要是工作强度、专注、并行、时间沟通、质量风险，职业专属参数只是其中一组；[配置页](../../../ui/setup.js)也沿用同一组织方式。
2. [通用引擎](../../../sim/engine.js)主要按预算分配工作量、推进任务、抽取错误并增加返工；专业操作经职业适配器写入交付物。主动检查会调用职业检查后，统一把已有错误标为解决。
3. [评分](../../../sim/scoring.js)四职业共用六维和同一组权重，职业差异主要通过交付、质量、关系和风险量传入。当前没有各自完整的专业验收指标体系。
4. [交互入口](../../../main.js)允许切换文件、工作表、会话和窗口视角；这些属于观察。PS 工具及图层主要是展示，VS Code 代码、终端和提交由仿真状态产生，玩家尚未通过软件形成独立生产决策。
5. [存储](../../../meta/storage.js)使用同一 `gamex:v1:` 前缀。若以后在同一站点提供单职业产品，必须定义各自策略、历史和当前会话的归属。

### 有效约束、假设与未知项

- 用户已确认的目标：强化职业独特软件与玩法，分析拆分边界。
- [原 V1.2](../REQ-20261109143131-单职业桌面模拟器/20261109143131-原始开发要求V1.2.md)定位为自动职场模拟与低频策略；局内只有第 10 轮加班选择改变结果，视觉交互不能改状态。本轮没有直接取消此约束。
- 设计建议：维持自动办公，先在两个职业样片中评估少量有意义的专业决策；无需让玩家掌握真实编程或完整 Photoshop 操作。
- 尚未确认或验证：是否接受新增局内专业决策点、理想操作频率、是否分别发布独立入口、玩家能否明显感受到两种玩法。

## 判断依据

1. 职业状态已不同，而玩家可选策略、通用推进和结算仍相似，因此首要工作是加强职业决策及专业因果。单独命名和入口可以改善定位，但不会自行形成这些因果。
2. 程序员处理代码依赖、缺陷与测试；设计师处理信息层级、视觉方案与客户偏好。它们需要不同的生产与验收规则，共享一个细粒度“工作推进规则”会限制差异化。
3. 两者仍需要同样的桌面、窗口、消息、播放控制和持久化能力。当前任务栏、头像等公共体验的维护已说明，共享这些底层有实际价值。
4. 因此建议按“共享桌面底层 + 职业独立玩法包”组织，先验证两个职业的体验差异，再决定独立发行。内容上可按独立职业游戏设计，工程上先共用一套基础设施。

## 备选方案与排除依据

| 方案 | 玩法收益与成本 | 判断 |
| --- | --- | --- |
| 维持通用推进和评分，只增加软件画面、动画及职业参数 | 公共体验维护容易，但专业选择仍可能相互替换 | 可继续完善拟真，不足以单独承担本次差异化目标 |
| 立即复制成四套独立工程、仓库和发布 | 产品名称清楚；相同玩法会被一起复制，公共修复、版本及存档兼容需要多处维护 | 当前暂缓，等职业玩法有独立发布价值后再评估 |
| 同仓共用底层，职业分别拥有策略、生产、软件动作与验收；按需要构建独立入口 | 能优先投入职业差异，同时集中维护公共体验 | **推荐** |

职业命名可以采用《程序员桌面模拟器：2026》等系列形式；其他标题、入口与仓库数量仍属于后续产品决策，不视为已批准的发布计划。

## 每个软件需要形成什么玩法

下表为设计建议，不是对当前已实现能力的描述。选择可以先做成开局的职业执行策略；若放到局内，必须走下文的决策检查点方案。

| 职业与软件 | 核心生产循环 | 值得权衡的选择 | 软件可见反馈与专业验收 |
| --- | --- | --- | --- |
| 程序员 · VS Code | 理解需求 → 定位问题 → 实现/修复 → 测试 → 评审交付 | 补丁或重构；先测哪些边界；接受变更时保留什么范围；何时偿还技术债 | 具体诊断、代码变更、失败用例、测试结果和提交门禁；未通过必需测试不能显示已通过交付 |
| 设计师 · Photoshop | 解析 Brief（设计任务书）→ 构图及图层 → 方案比较 → 反馈改稿 → 导出验收 | 先澄清或探索；单方案精修或多方案分配；版式取舍；可编辑图层或快速合成 | 画布方案实际不同；图层结构影响改稿成本；反馈对应明确视觉变化；尺寸、文案、品牌和安全区约束通过后再验收 |
| 财务 · Excel | 核对凭证 → 公式与关联表 → 追踪异常 → 审批及结账 | 核对范围；先检查哪些关联；缺失凭证上报或暂挂；异常修复的优先级 | 原始凭证与单元格可追踪，错误沿依赖传播；数字、来源和审批状态共同决定是否可交付 |
| 产品经理 · Word/需求看板（看板为拟新增） | 澄清目标 → 范围与优先级 → 评审协商 → 变更管理 → 基线验收 | 必做与延期；需求粒度；交付时间和范围交换；如何收敛冲突 | PRD（产品需求文档）、范围、依赖及验收条件一致；未确认的冲突不能通过增加文字量直接消失 |

程序员样片应验证“诊断、修复、测试、交付”各有状态和成本；不能仅增加一行测试通过文案。设计师样片应验证具体方案、客户需求和图层结构；多方案投入不应自动保证验收，审美反馈也应由可解释的任务偏好和约束产生。

## 怎么拆：四层边界

| 层次 | 职责归属 | 建议 |
| --- | --- | --- |
| 桌面基础 | 系统皮肤、窗口、图标、消息容器、播放和通用存储能力 | 共用，外观及观看方式继续不影响逻辑结果 |
| 职业玩法 | 任务依赖、策略、专业状态、故障、返工、职业事件和验收指标 | 按职业独立，允许不同的生产步骤和硬性条件 |
| 软件工作台 | VS Code、PS、Excel、Word 的观察视图、专业决策、动作表现与报告细节 | 跟随对应职业；微信容器共用，角色权责、消息意图和反馈内容由职业提供 |
| 产品与发行 | 名称、入口、引导、版本、存档命名空间和发布包 | 玩法验证后独立配置；同仓多入口可以满足第一阶段，独立仓库另行判断 |

现有 `sim/professions/` 与 `apps/` 可作为起点，先理清职责与契约，再按实施需要渐进归拢。建议边界如下，仅为说明，未创建这些目录：

```text
共享基础：桌面 / 消息容器 / 调度与种子 / 动作协议 / 回放 / 存储适配
职业模块：
  程序员：任务 + 执行策略 + 代码/缺陷/测试模型 + VS Code 工作台 + 工程验收
  设计师：任务 + 执行策略 + 方案/图层/修订模型 + PS 工作台 + 设计验收
  财务：任务 + 执行策略 + 凭证/公式/审批模型 + Excel 工作台 + 财务验收
  产品经理：任务 + 执行策略 + 范围/冲突/基线模型 + 文档与看板 + 需求验收
```

共享调度层分配资源并接收职业模块返回的语义动作；职业模块负责自己的正确性和交付条件。软件渲染器消费动作，不能在 DOM 内计算成功、随机生成返工或直接修改绩效。统一报告外壳可以展示不同的职业指标，职场关系与体力继续共用；职业核心评价不必继续使用完全相同的转换公式。

## 交互频率与引擎影响

### 路径一：维持原自动模式，先做深职业执行策略

把测试安排、修复/重构、设计探索/精修、改稿方式等放入开局的阶段执行计划。模拟器按照该计划操作软件，输出具体专业因果和交付物。这样可以先验证差异化，并保留前 10 轮计算、一次加班及完整回放的原契约。

### 路径二：自动办公中加入少量专业关键决策

推荐通过样片评估此方向，例如程序员遇到高风险缺陷时选择修复方案，设计师收到矛盾反馈时选择下一版方案。等待玩家时不倒计时、不默认选项，也不把每次打字或拖动变成必须操作。

这会改变原版“局内只有加班影响结果”的要求，实施前需明确版本与边界：

- 引擎按决策段计算；到决策点保存检查点，获得合法选择后才继续。不能预先算完前 10 轮，再让界面按钮看似改变既定结果。
- 决策进入版本化日志；相同种子、环境、策略及决策序列必须得到相同逻辑结果。
- 回放、刷新恢复和快进停在相同决策边界；浏览器播放节奏不参与领域计算。
- 新旧存档保持明确版本与归属；不能用界面状态猜测过去的选择，或删除旧版记录。

若样片表明关键决策破坏挂机体验，应采用路径一，保持专业策略与专业因果的深度。两条路径都不需要引入真实模型 API 或执行玩家的任意代码。

## 最终结论与执行计划

1. **先定义两个反差明显的样片。** 程序员使用一个有边界缺陷、变更和交付门禁的退款服务任务；设计师使用一个有明确品牌约束、偏好及改稿要求的海报任务。先完成程序员，再以设计师验证边界。
2. **建立各自的专业因果。** 每个样片明确主要状态、至少三种有收益和代价的专业选择、具体失败及交付条件；软件画面必须解释这些变化。当前专业模型继续作为基础。
3. **抽取经过验证的公共契约。** 让职业模块承担专业推进和验收，保留共享动作、桌面与存储底层。验证局内关键决策的必要性后，再决定是否升级引擎和存档版本。
4. **验证差异后扩展职业与发布。** 补齐财务与产品经理；当职业能独立说明自身玩法、内容及复玩价值时，再使用独立名称、入口和存档。仓库拆分依据发布与维护需要决定。

### 可证伪的检查点

- 隐去职业名和软件图标后，评估者仍能从主要策略、结果与失败原因描述职业差异；如果只剩同一套“投入、提速、检查、返工”，本轮差异化方案尚未达到目标。
- 相同任务/种子下，不同职业策略产生可解释的专业状态、交付物和验收差异；不同任务条件下存在合理取舍，不能始终由一个选项占优。
- 程序员的失败用例与修复范围有关，设计师的改稿与具体方案/图层有关；检查、诊断、修复与通过验收不能被当作同一个动作。
- 调整程序员模块不改变设计师既定场景的逻辑结果；调整桌面主题、窗口和速度也不改变职业结果。
- 评估者能从软件画面与日志说清“做了什么、为什么失败、改变哪个专业选择能改善”，而不只是在结算页看到一个总分。

这些是后续样片的建议验收标准，尚未做玩家试验，不代表体验差异或平衡已经验证。
