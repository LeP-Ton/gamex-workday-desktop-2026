## 推荐结论

采用一个源码仓库管理多个职业应用与共享包。每款职业游戏独立组合自己的玩法、软件工作台、内容、验收规则和产品配置，按职业构建产物；系统主题、窗口、回放和通用基础集中维护。

初期沿用现有原生 ES Modules、npm 与 Vite 工具链，使用 npm workspaces（工作区）管理本地包依赖、统一锁文件及按应用执行命令。[npm 官方说明](https://docs.npmjs.com/cli/v10/using-npm/workspaces/)

职业软件与玩法仍是本需求的主要目标；仓库结构提供隔离和复用能力，玩法差异须按[前阶段分析](20261110113343-分析与拆分建议.md)的样片标准验证。

## 目标目录

下面是目标边界示意，不代表已创建。实施按实际迁移建立目录，避免预建空包：

```text
apps/
  programmer-2026/       # 程序员游戏：代码/缺陷/测试模型及 VS Code 工作台
  designer-2026/         # 设计师游戏：方案/图层/改稿模型及 PS 工作台
  finance-2026/          # 财务游戏：凭证/公式/审批模型及 Excel 工作台
  product-manager-2026/  # 产品经理游戏：范围/基线模型及文档、需求工作台
packages/
  desktop-shell/        # 窗口、桌面布局、应用注册及系统界面装配
  os-themes/            # macOS / Windows 主题、系统装饰、资源与能力描述
  sim-core/             # 种子、事件/动作协议、调度与检查点基础
  playback/             # 回放、速度、暂停、跳转和动作投影
  messaging-ui/         # 微信界面、会话展示与通知容器
  persistence/          # 存储适配、迁移和版本校验能力
  ui-kit/               # 跨游戏确有复用的基础控件
```

现有 `apps/` 是软件渲染目录，目标 `apps/` 是职业产品目录。迁移时要明确移动与兼容关系，不能直接添加工作区配置后假定原有结构已经满足新边界。

职业特有代码先集中在应用内；当同一模块确实被两个应用复用时，再判断是否抽成独立包。迁移期保留旧合集入口及旧规则的兼容能力，避免新玩法上线造成原链接或存档失效。

## 共享底层的边界

| 包 | 应包含 | 依赖约束 |
| --- | --- | --- |
| `desktop-shell` | 窗口层叠、拖动缩放、焦点、应用注册、可用桌面区域 | 通过应用清单接收软件名称、图标、菜单和工作区；不硬编码职业判断 |
| `os-themes` | 颜色/字体/尺寸变量、壁纸、系统图标、窗口按钮、菜单栏、Dock/任务栏及开始菜单 | 提供完整系统装饰与能力描述；主题切换不进入职业规则或评分 |
| `sim-core` | 确定性随机、事件顺序、动作结构、资源调度与检查点协议 | 专业生产步骤、错误处理和交付条件由职业提供，避免强制复用同一工作量推进算法 |
| `playback` | 观看游标、倍速、暂停、跳转、回放恢复 | 消费动作与决策边界，保持观看操作与业务结果分离 |
| `messaging-ui` | 微信窗口、联系人列表、消息气泡、头像及通知展示 | 人物、头像地址、对话意图、消息内容和业务后果由应用注入 |
| `persistence` | 读写、版本、迁移机制 | 应用提供命名空间与领域数据校验，不使用一个全局会话键覆盖所有产品 |

主题抽象包括结构能力，例如 macOS 菜单栏与 Dock、Windows 开始菜单与任务栏，以及窗口按钮位置。游戏内部的系统外观与真实宿主操作系统控制分开；现有网页全屏能力仍受浏览器约束，架构迁移不自动解决原生系统栏行为。

依赖方向为职业应用使用共享包；共享包不反向导入应用，也不注册全部职业。职业应用之间不直接引用。软件的具体操作、因果反馈与职业规则在同一应用内演进。

## 按职业组装与构建

每款应用应有自己的 `gameId`、名称、入口、任务包、角色、专业规则、软件工作区、验收报告、产品版本与存档规则。例如程序员应用组合桌面、两套主题、微信、回放和存储，以及自身 VS Code 与代码/缺陷/测试模型。

构建使用显式依赖：程序员入口只引用本职业模块及所需公共资源，避免通过全职业注册表、统一渲染器入口或图标通配导入，将 PS、Excel 等职业资源一起打入。

迁移后的目标命令示例，当前尚未配置这些工作区：

```sh
npm run dev --workspace=@gamex/programmer-2026
npm run build --workspace=@gamex/programmer-2026
npm run test --workspace=@gamex/programmer-2026
```

各应用独立生成 `dist/`，内部共享包可先提供 ESM 源码交给应用打包。软件图标属于对应应用或软件模块，系统图标属于主题资源，素材来源与原始许可继续随资源维护。

## 存档与版本

- 各职业使用不同命名空间，例如 `gamex:programmer-2026:v1`、`gamex:designer-2026:v1`；策略、当前会话与历史互相隔离。同域不同路径不会自然隔离 localStorage。
- 原 `gamex:v1:` 记录保留。后续导入按职业和版本校验，只迁移兼容数据，不覆盖其他产品记录。
- 区分产品版本、职业规则/评分版本、共享动作与存档协议版本；发布记录包含应用版本和源码提交，使构建及逻辑结果可追溯。
- 职业验收指标可以不同；历史比较限定于具有可比评分规则的记录，不把不同职业总分当成同一排行榜。

## 分职业发布的两种方式

### 初期建议：独立构建，单站点多入口

当前 GitHub Pages 可以承载一个完整静态站点，内含多个职业路径。例如在现有项目路径下规划 `programmer/`、`designer/` 等子目录，每款拥有独立标题、引导、存档和版本。这些路径尚未发布。

GitHub Pages 每个仓库最多一个项目站点，因此这属于多职业入口、同站点部署；不等于每个职业拥有独立 Pages 部署目标。[GitHub 官方限制](https://docs.github.com/en/pages/getting-started-with-github-pages/what-is-github-pages#types-of-github-pages-sites)

发布时必须组装完整站点产物，保留原入口及其他职业内容。初期可以全量构建后统一部署，不能只把程序员的 `dist/` 上传到站点根目录，导致其他入口消失。若要保持未发布职业的线上版本不变，需要按发布清单保留其已发布产物，再组成完整快照。

### 需要完全独立部署或回滚时：多个发布目标

仍保持一个源码 monorepo，每款应用把产物发送到自己的站点或发布目标。若全部继续使用 GitHub Pages，可使用各自仅存放发布产物的仓库；源码与共享底层仍集中维护，跨仓发布需配置对应权限。

因此应按发布要求选择：独立试玩地址和产品版本可先使用同站多入口；完全独立的部署、回滚或域名生命周期使用多个目标。独立软件玩法、产品构建和部署目标是三项分别验收的能力。

## CI 与迁移顺序

1. 固定现有基线和兼容入口，记录当前 37 项测试及浏览器流程证据，先验证结构迁移前后原版结果一致。
2. 优先抽取桌面壳与系统主题，再梳理公共回放、存储和事件协议。迁移阶段保持原玩法规则，版本升级另行记录。
3. 接入程序员独立应用与玩法样片，用设计师及 PS 样片验证共享接口是否足以容纳不同专业过程。
4. 完成职业产物及个人数据隔离后配置发布装配，逐步扩展财务和产品经理。

共享底层变更要回归所有已接入职业；职业变更重点测试该职业，整站发布仍需检查全部入口。首期沿用已有工具链，待真实构建耗时和依赖规模需要时再增加任务缓存或调度工具。

### 建议验收标准

- 程序员与设计师可分别构建，产物不携带其他职业工作台代码和专属资源。
- 公共包没有应用反向依赖，职业模型与软件反馈来自同一动作流。
- 切换系统主题不改变逻辑结果，公共外观修复能覆盖两款应用。
- 两应用在同域运行时存档、策略、历史互不覆盖，旧记录仍可恢复。
- 单站发布包含完整入口；独立部署时，一个职业发版或回滚不改变其他目标。
- 两个职业样片通过前阶段的玩法差异验收；仅目录或构建拆分不能作为该项通过依据。
