## 当前有效结论

- **建议拆分职业玩法模块，继续共用桌面底层；独立产品入口与名称在样片验证后按职业推出，暂缓四套独立工程。**
- 工程方案细化为 monorepo：职业应用独立组装、构建与管理数据，共用桌面壳、系统主题及基础包。当前 Pages 单仓一个站点，需要区分多入口统一部署与多目标独立部署，见[monorepo 架构与发布方案](20261110115137-monorepo架构与发布方案.md)。
- 现有四职业已经有不同的交付物、状态与风险链；不足主要在玩家决策、通用推进和评价口径，软件界面尚未充分成为玩法载体。
- 每个职业应拥有任务生产链、执行策略、专业状态、错误及返工模型、软件动作和验收规则；系统外壳、微信容器、窗口、播放、随机与事件协议可以复用。
- 优先制作程序员与设计师两个对照样片：一个验证缺陷定位、修复、测试与交付，一个验证构图、方案、反馈与改稿。两者反差足够大，适合检验共享底层的边界。
- 推荐评估“自动办公 + 少量软件关键决策”；原版只允许一次加班决策，若采用新模式，必须单独定义决策检查点、确定性与存档版本。保持原自动模式时，可先把职业选择前置为阶段执行策略。
- 全部依据、备选方案与实施顺序见[分析与拆分建议](20261110113343-分析与拆分建议.md)。
